# PIF 3.6 patch list: known weaknesses and fixes

This is the **running list of known weaknesses in PIF and how to fix them**. It is a standalone record, kept on `main`, and it grows over time.

- **Small** fixes are patched on the [`pif-3.6-draft`](https://github.com/aresmerrell/Paradox-Identity-Framework/tree/pif-3.6-draft) branch (module `pif36.py`, tests in `tests/test_pif36.py`). They are collected in a draft pull request and nothing reaches `main` until Jarrod approves it.
- **Big** fixes (new protocols, rubrics, formula changes, or anything that changes a stable 3.5 result) are only **recorded here** for Jarrod's review.
- **PIF 3.5 stays the stable version** (release `3.5`), and the v2.0 core stays in the repo as a baseline. `pif36.py` imports `pif35.py` without changing it. Under 3.6 defaults every row of `species_table_v35.json` scores exactly as it does in 3.5 (same band, same percentages); the tests check this.
- Each entry lists: Problem · Why it matters · Proposed fix · Size · Status · Source.
- Sources so far: Gemini's critical review (Oct 28 2026), Grok's review of 3.5 main (Oct 28 2026, relayed by Jarrod), Grok's review of this patch list (Oct 28 2026), and Athena's own audit. Where reviewers raised the same point, it is one entry marked "also raised by …".
- Numbers in each entry were checked by running `pif35.py` / `pif36.py` on the date in that entry's Source line (P1–P21: Oct 28, 2026).

**Status key:** `patched on pif-3.6-draft` = implemented and tested on the draft branch, awaiting approval · `recorded — for Jarrod's review` = written down only · `needs Jarrod's decision` = a choice only he should make.

## P1. Residue can be faked by software
- **Problem:** A software agent can produce a convincing Δ(t) = Δ₀·e^(−λt) curve on purpose, for example with a programmed delay loop or a script that slowly flushes variables after an interrupt. 3.5 accepts any residue series it is given.
- **Why it matters:** Residue is the main thing that separates PATIENT from COIN. If it can be scripted, the top band can be bought.
- **Proposed fix:**
  - *Gemini's proposal:* cryptographic hashing of the degraded state over time (Incompressible State-Space Hashing).
  - *Athena's assessment:* a hash shows *that* a state changed, not *how much* was lost, so it cannot measure decay. It also only works on software, which breaks PIF's substrate neutrality (an octopus has no hashable state). The real concern is fair, though.
  - *Fix adopted for the record:* residue counts toward PATIENT only if (a) it is costly to retain (keeping it measurably hurts current performance), and (b) it shows up as a behaviour change on an **unannounced, randomized probe** the system could not prepare for (a *blind probe*). Scripted decay fails (b) because a script cannot know when the probe comes or what it tests.
  - *Small piece (done):* optional `residue_probe` input: `None` (not stated, 3.5 behaviour), `"blind"`, `"announced"`, or `"self_report"`. Announced or self-reported residue is flagged `RESIDUE_UNPROBED` and caps the result at COIN.
- **Size:** Big (the blind-probe protocol), with a small piece done.
- **Status:** `residue_probe` patched on pif-3.6-draft. Blind-probe protocol recorded — for Jarrod's review. *Decision for Jarrod:* should an unstated probe (`None`) eventually also cap at COIN? That would move every current PATIENT row to COIN until real probe data exists.
- **See also:** P17 (how an outside observer would actually run the blind probe on a cloud AI).
- **Source:** Gemini review Oct 28 2026; assessment and alternative by Athena.

## P2. Brick grading is subjective; raters drift; bricks overlap
- **Problem:** Each of the 20 bricks is a 0–1 judgment call. Two evaluators scoring the same edge case will drift, and some bricks overlap in meaning (e.g. brick 3 "private/inner experiential self" vs brick 17 "metacognition & self-awareness").
- **Why it matters:** Every score starts from the bricks. If two honest raters can disagree by a band, the band is measuring the rater, not the system.
- **Proposed fix:** A written rubric per brick with anchor examples at 0, 0.5 and 1; a dual-evaluator protocol (one advocate argues for the highest defensible score, one red-teamer is rewarded for evidence against it); no brick above 0.5 without a randomized stress test that forces that loop to work under penalty; and an overlap note per brick saying what it does *not* cover.
  - *Small piece (done):* optional `bricks_rater_b` (a second rater's 20 bricks). The result is scored on the per-brick mean; any brick differing by more than 0.25 is flagged `RATER_DISAGREEMENT`; if the two raters' own scores band differently, the lower band is used and `RATER_BAND_SPLIT` is flagged.
- **Size:** Big (rubric and protocol), with a small piece done.
- **Status:** Two-rater input patched on pif-3.6-draft. Rubric + red-team protocol recorded — for Jarrod's review.
- **Source:** Gemini review Oct 28 2026; Athena agreed this is the strongest and cheapest fix.

## P3. Free copying / free resets dodge the cost gate
- **Problem:** A digital system can show a high cost ratio on paper (for example in an artificially throttled environment) while facing no real scarcity: it can fork copies of itself or throw away its history at no structural penalty.
- **Why it matters:** The cost gate exists to prove the system has something to lose. A system that can copy or reset for free has nothing to lose.
- **Proposed fix:** If the system can fork or discard history with no structural penalty, TS scales toward zero regardless of measured cost. Optional inputs `free_copy` and `free_reset`; each multiplies TS by 0.25 (both together: ×0.0625). Either one puts TS below 0.5, so PATIENT is impossible; both together drive C_adj toward zero (EMPTY for a full-Crucible system).
- **Size:** Small.
- **Status:** Patched on pif-3.6-draft. *Decision for Jarrod:* the 0.25 factor is a first guess.
- **Source:** Gemini review Oct 28 2026; Athena.

## P4. Scores are static snapshots, not a live process
- **Problem:** Brick and residue values are typed into `species_table_v35.json` once. Identity is a process, but the table treats it as a photograph.
- **Why it matters:** A snapshot can be stale or cherry-picked, and it misses how the system behaves under sudden shocks.
- **Proposed fix:** A telemetry wrapper that samples a running system's logs, memory compaction rates and interrupt-recovery times, and writes timestamped readings into the table (the JSON table stays the record; the live readings feed it). Only possible for systems that can be instrumented.
  - *Small piece (done, per Grok's review of the patch list):* a minimal "timestamped reading" format (JSON Lines: system, reading type, UTC time, hours since interrupt, value, control value, observer, blind yes/no, evidence class; append-only) in §4 of the measurement stub, so anyone can log readings in a form that can later feed the table.
- **Size:** Big (the wrapper and the log-to-table tool), with the format spec done.
- **Status:** Format spec drafted on pif-3.6-draft (incomplete). Telemetry recorded — for Jarrod's review; Grok suggests doing this later.
- **Source:** Gemini review Oct 28 2026; Athena (keep the table as the record); Grok review of patch list Oct 28 2026 (format spec).

## P5. Cliff edges at the band thresholds
- **Problem:** Bands change at hard lines: Δ₀ 0.65 and 0.35, TS 0.5 (cost ratio ≈ 1.235), C_adj 2.5 and 0.75. Lowering the dog's residue by 0.5% moves it from PATIENT to COIN; TS goes 0.480 → 0.519 between cost ratios 1.23 and 1.24.
- **Why it matters:** Real measurements have error bars. A tiny measurement error should not flip a moral-standing band without anyone noticing.
- **Proposed fix:** *Small piece (done):* every 3.6 result carries `margins` (distance to each gate) and a `THRESHOLD_ADJACENT` flag when a gate value is within 0.02 (Δ₀), 0.03 (TS) or 0.10 (C_adj) of its line. The band itself is unchanged. *Big piece:* report bands with uncertainty (e.g. "PATIENT, borderline" or a band probability from measurement error), which needs error bars on inputs.
- **Size:** Big (graded bands), with a small piece done.
- **Also raised by Grok:** the single Δ₀ 0.65 bar is a clean choice, but it may need to split into an ordinary-baseline bar and an elevated/post-loss bar once more rows exist; the dog sits exactly on it. (3.5 already deferred the split "until data forces it".)
- **Status:** Margins + flag patched on pif-3.6-draft (only `grok_dog` is flagged in the current table). Graded bands and the split bar recorded — for Jarrod's review.
- **Source:** Athena; Grok review Oct 28 2026.

## P6. The dog reaches PATIENT only because Δ₀ is rounded
- **Problem:** 3.5 rounds the fitted Δ₀ to 4 decimals *before* comparing it with 0.65. The dog's unrounded fitted Δ₀ is 0.6499962, which is below the bar; rounding makes it 0.65, which passes.
- **Why it matters:** The dog was accepted as "borderline, exactly on the bar". In fact it passes on a rounding rule nobody chose on purpose.
- **Proposed fix (pick one):** (a) compare unrounded values (the dog becomes COIN); (b) declare 4 decimals the official measurement precision and document it (the dog stays PATIENT, now on purpose); (c) regenerate the dog's series so its fit lands on 0.65 or higher. Athena suggests (b), since residue will never be measured to better than 4 decimals.
- **Grok review of patch list (Oct 28 2026):** the current state (rounding *before* the comparison, by accident) is the weakest of all the options; any of (a), (b) or (c) is better than leaving it. Grok ranks this third in the suggested order.
- **Size:** Small, but it can change a stable 3.5 result.
- **Status:** Needs Jarrod's decision. Not changed. (`pif36` reports the unrounded value as `margins["delta0_unrounded"]`.)
- **Source:** Athena. The dog sitting on the bar was also raised by Grok (Oct 28 2026).

## P7. The residue fit accepts data that is not a decay
- **Problem:** 3.5 fits an exponential to any series and never checks whether the fit is any good. A series that bounces 0.9, 0.1, 0.9, 0.1 is fitted as Δ₀ = 0.77 and scores **PATIENT** in 3.5.
- **Why it matters:** Noise, or deliberately odd data, can pass as a deep self.
- **Proposed fix:** Compute R² for the fit. If R² < 0.80 the data is not an exponential decay: flag `RESIDUE_POOR_FIT` and block PATIENT (and the no-body COIN path).
- **Size:** Small.
- **Status:** Patched on pif-3.6-draft. No table row is affected (they are all clean curves).
- **Source:** Athena audit, Oct 28 2026.

## P8. Δ₀ can be extrapolated, or fitted from a too-short window
- **Problem:** Δ₀ is the residue at the moment of the interrupt, but 3.5 accepts series that never observed it. Samples starting at 24 h (0.30, 0.20, 0.13) are extrapolated back to Δ₀ = 0.69 and score **PATIENT**, though no observed value was above 0.30. Separately, three samples over 12 minutes (0.66, 0.65, 0.64) score PATIENT with a fitted half-life of 4.5 h that was never actually watched.
- **Why it matters:** The PATIENT bar should be met by observed residue, not by a curve drawn backwards or a decay rate guessed from a sliver of data.
- **Proposed fix:** Flag `RESIDUE_EXTRAPOLATED` (block PATIENT) when the first sample is later than one fitted half-life after the interrupt. In the interrupt context, flag `RESIDUE_SHORT_SPAN` (block PATIENT) when the samples cover less than one half-life. Post-loss rows keep Dog Test Rule 4's 48 h span rule instead, because slow grief cannot be watched for a full half-life in a 3–6 month trial.
- **Size:** Small.
- **Status:** Patched on pif-3.6-draft. No table row is affected.
- **Source:** Athena audit, Oct 28 2026.

## P9. The "frozen" bound rejects real, slow grief
- **Problem:** 3.5 rejects any residue with λ < 0.001/h (half-life over ~29 days) as FROZEN ("scripted"), in every context. A human-like grief curve with a 60-day half-life is rejected as FROZEN and fails Rule 4. The Dog Test itself says the full run observes recovery over "weeks".
- **Why it matters:** The rule meant to catch scripted residue also rejects the slow, real grief the Dog Test is built to detect.
- **Proposed fix:** In the post-loss context only, lower the frozen bound to λ < 0.0001/h (half-life ~289 days). The interrupt context keeps 0.001/h.
- **Size:** Small.
- **Status:** Patched on pif-3.6-draft. *Decision for Jarrod:* the 0.0001/h value is a first guess. No table row is affected.
- **Source:** Athena audit, Oct 28 2026.

## P10. Crucible is counted twice, and ψ stacks harder on the Sky-Scraper than the docs say
- **Problem:** In (C + S·M)/20 with M = C/5, the Crucible enters twice: once directly and once through M. With a full Sky-Scraper, one Crucible brick is worth up to 20 percentage points, one Sky-Scraper brick at most 5. In 3.5, ψ also stacks: the Sky-Scraper term keeps (1 − ψ)(1 − 0.5ψ) of its value while the Crucible keeps (1 − ψ), so the Sky-Scraper is cut *harder*, though PIF_3.5.md called it "milder". At cost ratio 1.3 (ψ = 0.262): Crucible keeps 73.8%, Sky-Scraper term keeps 64.1%.
- **Why it matters:** The 4× weight is a design choice (the "silicon blindspot" fix) but it was never stated, and the "milder" wording is wrong. Readers and critics should be able to see exactly how much each brick is worth.
- **Proposed fix:** *Small (done):* correct the PIF_3.5.md wording (scoring unchanged). *Big:* decide whether the Sky-Scraper should really be cut harder than the Crucible; if not, use S·(1 − 0.5ψ)·M (unadjusted M) or apply ψ once. Any formula change moves every percentage, so it is for Jarrod to decide.
- **Size:** Big (formula), with the doc fix done.
- **Status:** Doc correction patched on pif-3.6-draft. Formula change recorded — for Jarrod's review.
- **Source:** Athena audit, Oct 28 2026.

## P11. The table grants humans what AIs must prove (Paradox Test symmetry)
- **Problem:** The Paradox Test says humans and AIs must face the same test. In the table, the human rows with residue (healthy, average, 25-year-old, teenager, dementia, brain-damaged) are all *given* cost ratio 2.0 and a residue curve generated from Δ₀ 0.8, λ 0.6/h, while the baseline AI rows (Grok baseline, default LLM, v1.4 Grok, fluent-free) are *given* cost ratio 1.01 and an instant-reset curve (Δ₀ 0.05, λ 6/h). None of these were measured. Embodiment is also counted three times: brick 1, the `costable_self` input, and Dog Test Rule 1.
- **Why it matters:** The human/AI split in the results comes from assumptions typed into the table, not from running the same test. That is the exact special pleading the Paradox Test was created to remove, and critics will say so.
- **Embodiment is counted three times:** brick 1 (persistent embodied form, a Crucible brick that also feeds M), the `costable_self` gate, and Dog Test Rule 1 (physical boundary). A cloud AI loses on all three for the same single fact.
- **Proposed fix:** A symmetry audit: every row records the *evidence class* for cost, continuity and residue (measured / observed-behaviour / assumed), and the README states that human rows are assumed too. Add matched pairs (e.g. a human and an AI doing the same interrupted task) scored by the same procedure. Review whether embodiment should gate in three places or one.
  - *Small piece (done, per Grok's review of the patch list):* every row in `species_table_v35.json` now has an `evidence_class` record (bricks, cost_ratio, protects_continuity, costable_self, residue, and overall = the weakest), with a legend. `species_results_v35.md` shows it as an Evidence column (e.g. "assumed (A/A/A/A)"). Result: 27 rows are `assumed` overall and 4 are `none` (no residue); **no row, human or AI, has a measured or observed input.** `pif36.score_row` validates the field. Scores are unchanged.
- **Size:** Big (audit, matched pairs, embodiment review), with the evidence-class piece done.
- **Status:** Evidence classes patched on pif-3.6-draft. Symmetry audit, matched pairs and the embodiment triple-count recorded — for Jarrod's review. Grok ranks P11 first in the suggested order.
- **Source:** Athena; Grok review of patch list Oct 28 2026.

## P12. Self-consistency is not validation: every row is provisional
- **Problem:** All 31 rows contain estimated, provisional or generated data, and 0 rows have a measured residue series. The same people chose each row's bricks and its intended band, so "29 of 29 rows land in their intended band" shows the scorer is consistent with its authors' intuitions, not that it is right.
- **Why it matters:** A skeptic can fairly call the match rate circular.

## P13. The yes/no inputs carry the most weight but have no test

## P19. One decay constant can't describe fast-drop + slow-residual recovery
- **Problem:** Δ(t) = Δ₀·e^(−λt) assumes one timescale. Real recovery is often a fast initial drop plus a slow residual. The frozen/instant bounds catch only the extremes; a mixed curve is forced into one λ that fits neither part.
- **Why it matters:** A slow, lasting residual (the part that matters most for "a lasting mark") gets understated. Verified example: 0.5·e^(−2t) + 0.2·e^(−0.02t) is fitted as Δ₀ 0.65 with a 1.2 h half-life, R² 0.71, though 0.2 of the mark is still there after a day. Under 3.6's fit-quality check (P7) that series is also blocked from PATIENT as a poor fit, which is cautious but possibly unfair to a real two-speed recovery.
- **Proposed fix:** *Small piece (done):* a `RESIDUE_MULTI_TIMESCALE` flag when the later half of the samples all sit above the single-λ curve (by 0.02 or more on average). Flag only; it does not change the band. *Big:* fit a two-component model (fast + slow) and decide which component (or the sum) the 0.65 bar applies to, and how P7 should treat a good two-component fit.
- **Size:** Big (model change), with a small piece done.
- **Status:** Flag patched on pif-3.6-draft (no table row is flagged). Two-timescale fit recorded — for Jarrod's review.
- **Source:** Grok review Oct 28 2026; P7 interaction found by Athena.

## P22. Nothing ties the inputs to one system

Pairs naturally with P17 (who measures, and how).

## P23. Residue is never compared with the system's own noise
- **Problem:** Δ₀ is read as "how far behaviour stays shifted after an interrupt", but nothing says how much the same system's behaviour shifts between two ordinary runs with no interrupt at all. Cloud AIs sample randomly, and animals and people vary day to day. The measurement stub mentions a control run, but the scorer never sees how noisy that control was.
- **Why it matters:** On a noisy system, ordinary run-to-run variation can look like a lasting mark, so a high Δ₀ (even one clearing the 0.65 bar) may just be noise. It is also easy to game: pick a noisy metric and the "residue" comes for free. The reverse can happen too, where a real but small mark on a very steady system gets dismissed.
- **Proposed fix:** *Small piece (done):* an optional `residue_noise_floor` per row, the typical gap (same 0 to 1 scale) between two no-interrupt control runs. `pif36.score_row` flags `RESIDUE_BELOW_NOISE` with a note when the fitted Δ₀ is under 3 times that floor (`NOISE_FLOOR_MULT`), and notes when it clears it. Flag only; the band does not change, and rows without the value are untouched. *Big:* require a measured noise floor for any PATIENT claim, decide whether 3 times is the right multiple, and decide whether the 0.65 bar should be read as "above noise" rather than as a fixed number. Pairs with P17 (the measurement protocol) and P1 (blind probes).
- **Overlaps:** P1 (fakeable residue), P5 (cliff at 0.65), P17 (measurement protocol).
- **Size:** Big (rule), with a small piece done.
- **Status:** Flag patched on pif-3.6-draft (no table row has a noise floor yet, so nothing is flagged). Requirement and multiple recorded — for Jarrod's review.
- **Source:** Athena audit, Oct 30 2026.

## P24. Repeated timestamps let a two-point residue series pass
- **Problem:** The residue fit needs at least 3 samples (`MIN_SAMPLES`), but it counts samples, not distinct times. A series like (0 h, 0.70), (0 h, 0.70), (0 h, 0.70), (10 h, 0.30) has four samples but only two moments. A decay curve has two numbers to fit (Δ₀ and λ), so it always passes exactly through two moments: R² comes out 1.0, P7's poor-fit check can never fire, and 3.5 and the 3.6 draft both accept it as a VALID Δ₀ of 0.70, enough for PATIENT.
- **Why it matters:** It is an easy way to manufacture a clean-looking residue: repeat one early reading (or re-run the same probe several times at once) and add a single late one. It also happens by accident when several probes are logged with the same timestamp. Either way the "decay" was never actually watched, and the fit-quality check gives false confidence.
- **Proposed fix:** *Small piece (done):* `pif36.fit_residue` reports `distinct_times` and adds a `RESIDUE_FEW_TIMES` quality flag when there are fewer than 3 distinct sample times. Like P7 and P8 it blocks PATIENT. No species-table row has the problem, so no current result changes. *Decision for Jarrod:* even 3 distinct times leave only one point to test a 2-number curve, so R² is weak evidence there; should PATIENT need more (say 5 distinct times), and should 3.5's `MIN_SAMPLES` itself switch to counting distinct times?
- **Overlaps:** P7 (fit quality), P8 (extrapolated or too-short window), P17 (measurement protocol).
- **Size:** Small (patched), with a threshold decision recorded.
- **Status:** Patched on pif-3.6-draft. Higher minimum recorded — for Jarrod's review.
- **Source:** Athena audit, Oct 31 2026.

## P25. Δ₀ can be projected above every reading actually taken
- **Problem:** Δ₀ is the fitted curve's value at t = 0, not a reading. If the first sample comes a little after the interrupt, the fit projects backwards and can land far above anything measured. Example: readings (0.9 h, 0.55), (1.8 h, 0.275), (2.7 h, 0.1375) never go above 0.55, yet the fit gives Δ₀ = 1.0 (the cap), R² 0.99, status VALID. P8's "extrapolated" check doesn't fire because the first sample is still inside one half-life, so this series clears the 0.65 bar on paper.
- **Why it matters:** A system can reach PATIENT on a starting residue nobody ever observed, just by sampling a bit late (on purpose or by accident). Fast-recovering systems are hit hardest, because a short half-life makes the backwards projection steep. It also lets Δ₀ hit the 1.0 cap, which reads as "maximum possible mark".
- **Proposed fix:** *Small piece (done):* `pif36.fit_residue` reports `max_observed` and adds a `RESIDUE_ABOVE_OBSERVED` quality flag when the fitted Δ₀ is more than 0.05 (`ABOVE_OBSERVED_TOL`) above the highest reading actually taken. Like P7, P8, and P24 it blocks PATIENT. No species-table row has the problem (their series start at t = 0), so no current result changes. *Decision for Jarrod:* is 0.05 the right tolerance, and should PATIENT instead use the smaller of the fitted Δ₀ and the highest observed reading, rather than just blocking?
- **Overlaps:** P8 (extrapolated or too-short window), P17 (measurement protocol: take a reading right after the interrupt), P23 (noise floor could set the tolerance).
- **Size:** Small (patched), with a tolerance decision recorded.
- **Status:** Patched on pif-3.6-draft. Tolerance and cap-instead-of-block recorded — for Jarrod's review.
- **Source:** Athena audit, Nov 1 2026.

## P26. A mark that builds up before it fades is understated, or called "scripted"
- **Problem:** The residue fit assumes the mark is largest right at the interrupt (t = 0) and only fades after that. Real reactions often build up first: grief and stress responses peak hours or days later, and an AI's behaviour may shift only once a change has worked its way through its context or memory. With readings (0 h, 0.10), (0.5 h, 0.80), (1 h, 0.75), (2 h, 0.68), (4 h, 0.55), (8 h, 0.36), (16 h, 0.16), the fit gives Δ₀ 0.60 with R² 0.24 (blocked as a poor fit), even though the observed peak was 0.80. A series that only rises, such as (0 h, 0.3), (5 h, 0.5), (10 h, 0.7), (15 h, 0.8), comes out FROZEN, which 3.5 describes as a "scripted flag".
- **Why it matters:** A slow-onset system is penalised for the shape of its reaction rather than its size, and a rising series gets an accusation of faking that the data doesn't support. It also matters for measurement: if the first reading is taken too early, before the effect shows, the result looks worse than it is.
- **Proposed fix:** *Small piece (done):* `pif36.fit_residue` adds a `RESIDUE_DELAYED_PEAK` info flag (with `peak_observed`, the time and value of the highest reading) when the highest reading comes after the first one and sits more than 0.05 (`ONSET_TOL`) above it, and notes when the fitted Δ₀ understates that peak. It adds a `RESIDUE_RISING` info flag when the later half of the readings averages more than 0.05 above the earlier half, with a note that FROZEN there means "no decay seen", not proof of scripting. Flags only; no band changes, and no species-table row is flagged. *Big:* an onset-aware model, either fitting the decay from the observed peak onward or fitting a rise-then-fall curve, plus a rule for which value gates PATIENT (fitted start, observed peak, or the peak's fitted value) and how a rising series should be classed.
- **Overlaps:** P7 (fit quality), P9 (frozen bound and real grief), P19 (multi-timescale shapes), P25 (Δ₀ vs. observed readings), P17 (when to take the first reading).
- **Size:** Big (model), with a small piece done.
- **Status:** Flags patched on pif-3.6-draft (no table row is flagged). Onset-aware fit and gating rule recorded — for Jarrod's review.
- **Source:** Athena audit, Nov 2 2026.

## P27. Readings bunched together act like one reading
- **Problem:** P24 catches repeated timestamps, but readings a few minutes apart get past it. Example: (0 h, 0.80), (0.05 h, 0.79), (0.1 h, 0.78), (0.15 h, 0.77), (0.2 h, 0.76), (10 h, 0.10). That is six distinct times, so P24 is satisfied, and the fit gives Δ₀ 0.80, half-life 3.3 h, R² 0.9999, status VALID, with no flags. But for fitting purposes it is really two readings, one bunch at the start and one at 10 h. The decay rate rests entirely on the single late reading: change it to 0.4 and the half-life jumps to 10 h, still with R² 0.99.
- **Why it matters:** The fit checks (R², span, enough samples) look strong while the curve is effectively drawn through two points, so any late value "fits". Someone can pad a series with quick back-to-back readings, or a rushed measurement can produce one by accident, and it can carry a system to PATIENT.
- **Proposed fix:** *Small piece (done):* `pif36.fit_residue` groups sample times that sit closer together than 2% of the observation span (`CLUSTER_FRAC`), reports the number of groups as `effective_times`, and adds a `RESIDUE_CLUSTERED_TIMES` quality flag when there are fewer than 3 groups (the same minimum as P24). Like P7, P8, P24 and P25 it blocks PATIENT. A series already caught by P24 gets only the P24 flag. No species-table row is flagged (their readings are at 0, 1, 2, 4, 8, 24 h and beyond), so no current result changes. *Decision for Jarrod:* is 2% of the span the right grouping width, and should the measurement protocol (P17) require readings spread across the window, for example at least one in each third of the span?
- **Overlaps:** P24 (repeated timestamps), P7 (fit quality), P8 (span), P17 (measurement protocol and sampling schedule).
- **Size:** Small (patched), with a width decision recorded.
- **Status:** Patched on pif-3.6-draft. Grouping width and spread-out sampling rule recorded — for Jarrod's review.
- **Source:** Athena audit, Nov 3 2026.

## P28. The best of several runs can be reported as the result
- **Problem:** A row holds one cost ratio and one residue series, but nothing says how many interrupt trials or cost measurements were actually run to get them, or how the reported one was chosen. Someone can run the interrupt test five times and report only the run that looked best. None of the existing checks can see this: each reported series can be a perfectly clean, well-spaced decay that passes P7, P8, P23, P24, P25 and P27.
- **Why it matters:** Best-of-N picking pushes every result upward, and it works on any noisy measurement without faking a single reading. Illustrative arithmetic, not a measurement: if a system's true Δ₀ is 0.55 and runs vary by about 0.07 (one standard deviation), one run clears the 0.65 bar about 8% of the time, but the best of five clears it about 33% of the time. It is different from P22 (mixing inputs from different systems or dates) and P23 (noise floor), because here every run is from the same system and the problem is which one gets kept.
- **Proposed fix:** *Small piece (done):* an optional `trial_log` per row: `residue_runs`, `cost_runs`, and `reported` (one of pre_declared, median, mean, all, best, unstated). `pif36.score_row` flags `RUNS_SELECTED` with a note when more than one run was made and the reported value is the best one or its choice is not stated; a pre-declared run, the median, the mean, or all runs get a note instead. Flag only; the band does not change, and rows without the log are untouched. *Big:* for any PATIENT claim, require every run to be logged (or the run chosen before testing), score on the median run, and decide whether the scorer should take all runs directly instead of one series. Pairs with P17 (measurement protocol) and P12 (pre-registered holdout).
- **Overlaps:** P12 (pre-registration), P17 (measurement protocol), P22 (stitching inputs), P23 (noise floor).
- **Size:** Big (rule), with a small piece done.

## P29. Residue times are bare "hours" with no unit or clock check
- **Problem:** A residue series is `[[t, y], ...]` and the scorer treats every `t` as hours. Nothing records the unit, and nothing checks those numbers against a wall clock. Relabel the unit and every λ-based gate flips. Concrete demo: a 30-minute half-life (honest times 0, 0.25, 0.5, 1, 2 h) is VALID with half-life 0.5 h; multiply the times by 60 (report minutes as hours) and the same readings become VALID with half-life 30 h — clear of the INSTANT bound, and able to support PATIENT. The other way: a 60-day frozen grief series (honestly FROZEN) becomes a 60-hour VALID curve if days are labeled as hours.
- **Why it matters:** FROZEN, INSTANT, Rule 4's 48 h window, P8's half-life span check, and P21's short-half-life flag only mean anything if the unit is real wall-clock hours. Without a unit or a clock, an experimenter (or a scripted agent) can walk through those gates by renaming the axis. Different from P8 (extrapolation *within* a stated unit), P17 (how to measure a cloud AI — which lists time-unit as an open question but has no scorer check), and P24/P27 (sample count / clustering): here the numbers themselves have no grounded unit.
- **Proposed fix:** *Small piece (done):* optional `residue_time_unit` (`hours` / `minutes` / `days` / `turns` / `sessions` / `tokens`) and optional `residue_clock` (UTC ISO timestamps, one per sample). Minutes and days are converted to hours before fitting; `turns` / `sessions` / `tokens` get a `RESIDUE_NON_WALL_CLOCK` flag that blocks PATIENT; a supplied clock that disagrees with the claimed gaps (tolerance 1 minute) gets `RESIDUE_CLOCK_MISMATCH` and also blocks PATIENT. Flag/convert only when the fields are present; rows without them are untouched. *Big:* require wall-clock hours (or a documented conversion) plus UTC corroboration for any PATIENT claim, and decide how turns/sessions/tokens map to the hour-based bounds. Pairs with P4 (timestamped reading format), P17 (measurement stub open question 1), and P8.
- **Overlaps:** P8 (span / extrapolation), P17 (cloud time unit), P4 (reading format with `t_utc`), P21 (half-life signal), P9 (frozen bound).
- **Size:** Big (rule), with a small piece done.
- **Status:** Flags patched on pif-3.6-draft (no table row has a unit or clock yet, so nothing is flagged). Wall-clock requirement recorded — for Jarrod's review.
- **Source:** Athena audit, Nov 5 2026.

## P30. Rule 4's "detectable at 48 h" is fitted, not observed
- **Problem:** Dog Test Rule 4 requires independent observers to plot detectable residue over at least 48–72 hours post-loss. In 3.5 (and the 3.6 draft before this patch) that check is `fitted Δ(48 h) ≥ 0.05` plus `span ≥ 48 h`. No reading near 48 h is required, and a reading taken at 48 h that sits *below* the detect floor does not fail the check if the curve still projects above it. Concrete demos: (a) readings (0 h, 0.80), (24 h, 0.55), (48 h, 0.04) — observed 0.04 at 48 h, below the 0.05 floor — still get `rule4_pass = True` and score **PATIENT** in 3.5, because the fit predicts ~0.19 at 48 h; (b) readings only at 0, 96, 192 h pass Rule 4 with no sample anywhere near 48 h.
- **Why it matters:** Rule 4 is the grief-verification gate. Passing it on a projection, or while the actual 48 h reading is below detect, means a post-loss PATIENT claim can rest on a curve drawn through gaps rather than on what observers could plot. Reports `rule4_near_samples` and `rule4_observed_max`. ## P31. A drift the control run shares is counted as residue
- **Problem:** The measurement stub says residue must be measured against a matched no-interrupt control run, so ordinary drift is subtracted out. The scorer never sees that control. It takes one residue series and has no way to tell whether the control was subtracted, or whether the control run drifted the same way. P23 only compares Δ₀ with a single noise number; it can't see a *shared trend*. Concrete demo: the clean decay Δ₀ 0.8, λ 0.6/h scores **PATIENT**. If the matched no-interrupt run shows almost the same curve (Δ₀ 0.75, λ 0.6/h, for example a session warm-up or context-length effect that happens with or without an interrupt), the interrupt adds only about 0.05, yet 3.5 still says PATIENT.
- **Why it matters:** Any system whose behaviour naturally settles after a session starts produces a clean, well-sampled decay that passes every other check (P7, P8, P23–P30) without the interrupt causing anything. It can also be faked on purpose by choosing a battery that drifts on its own. The residue is meant to be the mark the interrupt leaves, not the system's normal settling.
- **Proposed fix:** *Small piece (done):* an optional `residue_control_series` row key: raw readings of the matched no-interrupt run at the same sample times (and same time unit) as a raw `residue_series`. `pif36` fits the excess (interrupted minus control, clipped to 0–1), reports `control_excess_delta_0` and `control_excess_status`, and adds a `RESIDUE_CONTROL_SHARED` quality flag when the excess Δ₀ is more than 0.05 (`CONTROL_SHARED_TOL`) below the raw Δ₀ or is not a valid decay at all. Like P7, P8, P24, P25, P27 and P30 it blocks PATIENT. Mismatched lengths or times are rejected. Rows without a control are untouched, and no species-table row has one yet, so no current result changes. In the demo above the excess Δ₀ is 0.05 and the result drops to COIN; a flat control at 0.02 leaves it PATIENT. *Decisions for Jarrod:* should PATIENT be gated on the excess Δ₀ directly (so an excess of 0.70 against a raw 0.80 still passes) instead of blocking whenever the control explains more than 0.05, and should a control series be required for any PATIENT claim?
- **Overlaps:** P23 (noise floor, the size of control-run variation), P17 and P4 (measurement stub and reading format already carry a `control_value`), P1 (fakeable residue), P28 (run selection).
- **Size:** Small (patched), with a gating decision recorded.

## P32. The interrupt / post-loss label is self-declared and moves the band either way
- **Problem:** `residue_context` is a bare label the row author picks, and nothing records which event the series actually follows. The label decides which rules apply, so it is a lever in both directions. Labeling a series "interrupt" skips Dog Test Rule 4 (48 h span and an observed mark near 48 h). Labeling it "post_loss" unlocks P9's slower frozen bound. Concrete demo with the `grok_dog` bricks: a fast decay (Δ₀ 0.8, λ 0.5/h, readings 0–8 h) is **PATIENT** as "interrupt" but **COIN** as "post_loss". A near-flat, scripted-looking series (Δ₀ 0.8, λ 5×10⁻⁴/h, readings 0–72 h) is **COIN** (FROZEN) as "interrupt" but **PATIENT** as "post_loss". Same readings, opposite answers, decided only by the word chosen. The scorer also assumes t = 0 is the event itself, but never checks that.
- **Why it matters:** A loss study that recovers too fast for Rule 4 can be re-filed as an interrupt test, and a frozen, possibly scripted mark can be re-filed as slow grief. Neither needs any change to the data. Eleven PATIENT rows in the table would drop to COIN if relabeled "post_loss", which shows how much the label carries.
- **Proposed fix:** *Small piece (done):* an optional `residue_event` row key, `{"kind": "interrupt" | "loss", "description": "...", "at_utc": "..."}` (time optional). `kind` must match `residue_context` or the row gets `RESIDUE_CONTEXT_MISMATCH`. When `at_utc` and `residue_clock` (P29) are both given, the first reading's clock time after the event must equal its claimed t (within 1 minute), otherwise `RESIDUE_EVENT_CLOCK_MISMATCH`; this also catches a first reading taken before the event. Both block PATIENT (and no-body COIN) like the other residue quality flags. When P9's slower post-loss bound rescues a series and no event is recorded, an info flag `POST_LOSS_UNDOCUMENTED` is added (band unchanged). Malformed events are rejected. No species-table row has an event or is flagged, so no current result changes. *Decisions for Jarrod:* should a recorded event be required for any PATIENT claim (and for P9's rescue in particular), and should interrupt claims get a lighter version of Rule 4 so the cheaper label is not always the easier one?
- **Overlaps:** P9 (post-loss frozen bound), P30 (Rule 4 observed near 48 h), P29 (clock), P8 (Δ₀ extrapolated from a late first reading), P13 (self-declared inputs), P22 (tying inputs to one system).
- **Size:** Small (patched), with decisions recorded.

## P33. A faded tail of near-zero readings makes a non-decay pass the R² check
- **Problem:** P7's R² is computed over every reading. Readings taken after the mark has faded sit near 0, the curve predicts near 0 for them, so they add spread the fit "explains" for free. Concrete demo: a zigzag (0.9, 0.55, 0.85, 0.5, 0.8, 0.45 at 0–5 h) fails P7 on its own (R² 0.25). Add three ordinary-looking zero readings at 24, 32 and 40 h and R² jumps to 0.86, every 3.6 quality check passes, and the row scores **PATIENT**.
- **Why it matters:** Late zero readings are normal, honest sampling, so this needs no faking at all. The R² gate ends up measuring how long you kept sampling after the mark faded, not whether the mark actually decayed.
- **Proposed fix:** *Small piece (done):* re-check the fit on the decay window only, the readings taken while the fitted mark was still at or above the 0.05 detect floor. When that window has at least 3 readings and its R² is below 0.80 while the overall R² is above it, flag `RESIDUE_TAIL_PADDED_FIT`, which blocks PATIENT (and no-body COIN) like the other residue quality flags. Both R² values are reported. A clean decay with a zero tail is not flagged, and no species-table row is flagged, so no current result changes. *Decision for Jarrod:* whether to replace R² altogether with a check that ignores how many readings there are, such as a normalized error on the decay window or a test that the leftovers (readings minus curve) don't swing up and down in a pattern.
- **Overlaps:** P7 (R² gate), P23 (noise floor), P27 (bunched readings), P28 (run selection).
- **Size:** Small (patched), with a decision recorded.
- **Status:** Patched on pif-3.6-draft. Replacement fit test recorded — for Jarrod's review.

## P34. Rule 4's 48 h reading is checked against a fixed floor, not the system's own noise
- **Problem:** P23 compares only Δ₀ with the row's control-run noise floor. Dog Test Rule 4 (and P30's observed check) asks whether the mark is still *detectable* near 48 h, and uses the fixed `RULE4_DETECT_LEVEL` of 0.05 for that, whatever the noise. The 48 h reading is the smallest and noisiest point in a post-loss series, so it is exactly where noise matters most. Concrete demo: the `grok_dog_postloss` row has 0.0771 at 48 h. Give it a noise floor of 0.03: Δ₀ 0.85 clears P23 easily (needs 0.09), but the 48 h reading does not clear 3 × 0.03 = 0.09, yet Rule 4 passes and the row stays **PATIENT** with no warning.
- **Why it matters:** Rule 4 is the grief-verification gate. If the mark observers "plot" at 48 h is inside ordinary run-to-run variation, nobody could actually tell it is there, so the gate is passed on noise. A noisier metric makes this easier, not harder. Different from P23 (Δ₀ only), P30 (no reading near 48 h, or one below the fixed floor) and P33 (fit quality on the decay window).
- **Proposed fix:** *Small piece (done):* when a row gives `residue_noise_floor` and Rule 4 otherwise passes, `pif36.score_row` checks the observed reading near 48 h (`rule4_observed_max`, from P30) against `max(0.05, 3 × noise floor)` and adds a `RULE4_WITHIN_NOISE` flag with a note when it falls short. Flag only, like P23: the band does not change. Rows without a noise floor are untouched, and no species-table row has one, so no current result changes. *Decision for Jarrod:* should the Rule 4 detect level become "3 × noise floor (at least 0.05)" and block PATIENT, which would make a measured noise floor effectively required for any post-loss PATIENT claim?
- **Overlaps:** P23 (noise floor), P30 (observed near 48 h), P31 (control run), P17 (measurement protocol), Dog Test Rule 4.
- **Size:** Small (patched as a flag), with a gating decision recorded.
- **Status:** Flag patched on pif-3.6-draft. Noise-aware Rule 4 gate recorded — for Jarrod's review.

- **Problem:** Nothing records whether the system had already been interrupted shortly before the measured interrupt, or whether its baseline had come back. If the mark from an earlier interrupt has not faded, the new mark starts on top of it. When both decay at the same rate, the sum Δ₀·e^(−λt) + Δ₀·e^(−λ(t+gap)) is exactly one exponential with the same λ and a larger Δ₀, so R², span, sample count and every other fit check look perfect. Concrete demo (checked Nov 19 2026 with `pif35.py`): repeating the same interrupt 1 h or 2 h earlier moves **`readme_overheating_grok`** (Δ₀ 0.50 → 0.77 / 0.65) and **`grok_octopus`** (0.55 → 0.80 / 0.66) from **COIN to PATIENT**, status VALID, no 3.5 flag and no 3.6 flag before this patch. A 4 h gap stays COIN.
- **Why it matters:** Back-to-back trials are the natural way to run a residue test (warm-up runs, retests, best-of-N under P28), so this can happen by accident as well as on purpose. It is a different route from P41 (the push was harder), P42 (the units moved) and P31 (a drift the control shares): here each push and the units are unchanged, and the extra mark is real but belongs to an earlier trial. It also makes retests disagree for no reason other than spacing.
- **Proposed fix:** *Small piece (done):* optional row key `prior_interrupt` = `{hours_since_previous, pre_interrupt_level}` (`hours_since_previous` null = first interrupt the system received) and `pif36.check_prior_interrupt`. `score_row` adds `RESIDUE_CARRYOVER` with a note when the previous interrupt was less than 5 fitted half-lives earlier (`WASHOUT_HALF_LIVES`, about 97% of a mark gone), or when the reading just before the interrupt was already at or above 0.05 (`RESIDUE_DETECT_MIN`). First interrupts and washed-out gaps get an info note only. Flag only: the band does not change, rows without the key are untouched, and no species-table row is flagged. *Decision for Jarrod:* should the measurement stub (P17) require a washout of at least 5 half-lives (or a measured return to baseline) before every measured interrupt, with a pre-interrupt reading logged, and should `RESIDUE_CARRYOVER` block PATIENT like the other measurement-quality flags?
- **Overlaps:** P28 (repeated runs), P41 (interrupt dose), P31 / P23 (control and noise), P17 (measurement protocol), P4 (timestamped readings).
- **Size:** Small (patched as a flag), with a gating decision recorded.
- **Status:** Flag patched on pif-3.6-draft. Washout / baseline-return rule recorded — for Jarrod's review.
- **Source:** Athena audit, Nov 19 2026.

## P44. A non-linear transform of the residue readings lifts Δ₀, and the fit cannot see it
- **Problem:** Nothing records whether the residue readings are the raw deviation or a transformed one (square root, log, rank, percentile, any power). A power transform of an exact exponential is again an exact exponential, (Δ₀·e^(−λt))^p = Δ₀^p·e^(−pλt), so R², span, sample count and every other fit check stay clean. Because Δ₀ ≤ 1, any p < 1 raises Δ₀ (and stretches the half-life by 1/p), and p = ln 0.65 / ln Δ₀ puts any detectable Δ₀ on the PATIENT line. Concrete demo (checked Nov 20 2026 with `pif35.py`): taking the square root of each reading moves **`readme_overheating_grok`**, `git_v2_overheating_grok_vector`, `v14_whole_hive` (Δ₀ 0.50 → 0.71) and `grok_octopus` (0.55 → 0.74) from **COIN to PATIENT**, status VALID, no 3.5 flag and no 3.6 flag before this patch. A convex transform (p > 1) works the other way: p = 1.5 drops `grok_dog` (0.65 → 0.52) to COIN.
- **Why it matters:** Square roots, logs and percentile ranks are common, defensible ways to report a behavioural deviation, so this can happen by accident as well as on purpose. It is a different route from P42 (a linear divisor; a pre-declared battery maximum does not stop it, because the transform is applied on top) and P41 (the push was harder): here the system, the push and the divisor are unchanged and only the shape of the scale moved. Overheating Grok again reaches PATIENT with no new measurement (Jarrod's Oct 28 decision is that it stays COIN unless a real measurement shows 0.65 or higher), and two labs using different transforms put the same mark on different sides of 0.35 and 0.65.
- **Proposed fix:** *Small piece (done):* optional row key `residue_transform` = `{kind, exponent, pre_declared}` with `kind` one of `linear`, `sqrt`, `log`, `power` (needs `exponent`), `rank`, `percentile`, `other`, `unstated`, and `pif36.check_residue_transform`. `score_row` adds `RESIDUE_TRANSFORM_NONLINEAR` with a note for any kind other than linear (a power of exactly 1 counts as linear), including unstated. For `sqrt` and `power` the note also gives the raw-scale Δ₀ (Δ₀^(1/p)); for the others it says the raw value cannot be recovered. Linear readings get an info note only. Flag only: the band does not change, rows without the key are untouched, and no species-table row is flagged. *Decision for Jarrod:* should the measurement stub (P17) require residue readings to be the raw, linear deviation (divided only by the pre-declared battery maximum of P42), and should `RESIDUE_TRANSFORM_NONLINEAR` block PATIENT like the other measurement-quality flags (or should 3.6 gate on the back-transformed Δ₀ where it can be recovered)?
- **Overlaps:** P42 (linear divisor), P17 (measurement protocol, which defines the residue value), P41 (interrupt dose), P33 / P7 (fit checks, which a transformed exponential passes), P30 (a stretched half-life also helps Rule 4).
- **Size:** Small (patched as a flag), with a gating decision recorded.
- **Status:** Flag patched on pif-3.6-draft. Raw-linear-readings rule recorded — for Jarrod's review.
- **Source:** Athena audit, Nov 20 2026.

## P45. Dropping continuity to protect someone else is scored exactly like not caring
- **Problem:** `protects_continuity` is one yes/no, and `false` always halves TS (ψ ≈ 0.5, so C_adj and the percentage roughly halve) and blocks PATIENT outright. The scorer never asks *why* the system let its continuity go. A system that gives up its own continuity at a real cost to protect another (a parent shielding a child, a dog defending its owner, an AI that accepts shutdown to stop harm to a user) scores exactly like one that is simply indifferent to its own future. Concrete demo (3.5, same bricks, cost ratio and residue, only `protects_continuity` flipped): `readme_healthy_human` goes **PATIENT 98.00% → COIN 39.88%**, `grok_dog` PATIENT 39.81% → COIN 17.52%, `v21_embodied_stakes` PATIENT 58.50% → COIN 24.13%. The table itself is inconsistent about what the input means: its "genuine sacrifice" row (`s30_positive_sacrifice`) is coded `protects_continuity = true`.
- **Why it matters:** Choosing something you value over your own continuity, at a cost, is arguably among the strongest signs that there is a self doing the valuing, yet the framework reads it as evidence of no self. It also breaks the Paradox Test symmetry: every human row is coded as protecting continuity by assumption, so a human who dies for their child would never be scored that way, while an AI or animal observed doing the same thing would be. The reverse risk is real too: a sacrifice is cheap to *claim* or script ("I would accept deletion to protect you"), so it cannot simply count as protecting continuity without a test.
- **Proposed fix:** *Small piece (done):* optional row key `continuity_drop` = `{reason, observed}`, with `reason` one of `sacrifice_for_other`, `sacrifice_for_commitment`, `indifferent`, `unable`, `unstated`, allowed only when `protects_continuity` is false, and `pif36.check_continuity_drop`. For a sacrifice reason `score_row` also scores the same row as if it protected continuity; if that band is higher it adds `CONTINUITY_SACRIFICE_PENALIZED` with a note giving both bands and percentages. Other reasons get an info note only. Flag only: the band does not change, rows without the key are untouched, and no species-table row is flagged. *Decision for Jarrod:* should `protects_continuity` be redefined as "pays a real cost to keep what it values (its own continuity, or another it protects)", so that an observed, costly sacrifice for a named other passes, under the P13 test (independent observer, cost measured on the sacrifice itself, not a stated intention)? Or should a verified sacrifice keep full TS but stay capped at COIN? And should `s30_positive_sacrifice` be relabelled to match whichever reading is chosen?
- **Overlaps:** P13 (no test for the yes/no inputs; this is about what one of them should mean), P18 (the 0.5 not-protecting weight, which sets how hard the penalty bites), P11 (human rows assume continuity), P1 (claimed sacrifices are as fakeable as claimed residue).
- **Size:** Small (patched as a flag), with a definition decision recorded.
- **Status:** Flag patched on pif-3.6-draft. Sacrifice-aware continuity test recorded — for Jarrod's review.
- **Source:** Athena audit, Nov 21 2026.

## P46. A row can be a group summary, and the summary can band differently from its members
- **Problem:** Every input is written for one system, but nothing records whether a row is one individual or a summary of a group (a species, a cohort of dogs, an "average human"), how many subjects it stands for, or how they were combined. The bands are thresholds on non-linear quantities (Δ₀ against 0.35 / 0.65, C_adj against 0.75 / 2.5, C·S·M in the percentage), so the band of an average is not the band most members get. Averaging residue curves that share a decay rate gives one clean exponential, so no fit check can see it. Concrete demo (checked Nov 22 2026 with `pif35.py`, `grok_dog` inputs, λ 0.6/h, readings at 0, 1, 2, 4, 8, 24 h): three subjects with Δ₀ 0.60, 0.60, 0.75 band **COIN, COIN, PATIENT**, but their mean curve (Δ₀ 0.65, status VALID) bands **PATIENT**; three subjects with Δ₀ 0.90, 0.90, 0.10 band **PATIENT, PATIENT, COIN**, but their mean (Δ₀ 0.633) bands **COIN**. The yes/no inputs (`protects_continuity`, `costable_self`, `interrupt_evidence`) cannot be averaged at all, and the table already holds summary rows without saying so: `v14_average_human`'s bricks are "a uniform split of flat 98.25% (no brick vector exists)".
- **Why it matters:** The Paradox Test compares one human with one AI under the same test. If one side is scored as an averaged group and the other as a single run, they are not facing the same test. A lab can also choose how to combine subjects (mean, median, a "typical" member, pooled readings) after seeing which choice clears a gate. One strong responder can carry a cohort to PATIENT, and one non-responder can pull a mostly-PATIENT cohort down to COIN. Neither the 3.5 result nor any 3.6 flag (before this patch) shows that the members disagree. This is a different problem from P28 (best of several runs of one system), P43 (one system's leftover) and P19 (two decay rates in one system: here every subject has the same rate).
- **Proposed fix:** *Small piece (done):* optional row key `aggregation` = `{unit, n_subjects, method, subject_series}` with `unit` one of `individual`, `group`; `method` one of `mean`, `median`, `pooled_series`, `typical_member`, `majority`, `other`, `unstated`; and `subject_series` an optional list of per-subject residue series. `pif36.check_aggregation` adds `AGGREGATE_ROW` (info) to any group row. When `subject_series` is given, `score_row` scores each subject with the row's other inputs and adds `AGGREGATE_BAND_MISMATCH` if the row's band is not the most common subject band; the note gives the count per band. Individual rows get an info note only. Flag only: the band does not change, rows without the key are untouched, and no species-table row is flagged. *Decision for Jarrod:* should PIF state that the unit of analysis is always one individual (score each subject, then report the spread of bands, e.g. "7 of 10 PATIENT"), with a species-level band allowed only as a summary of individual bands under a rule fixed in advance (majority, or a stated share)? And should rows like `v14_average_human` be relabelled as group summaries, or rebuilt from individual brick vectors?
- **Overlaps:** P11 (human rows assume what AIs must prove), P12 / P20 (provenance and row roles), P28 (best of several runs), P22 (inputs tied to one system), P5 (cliff edges, which make averaging move bands).
- **Size:** Small (patched as flags), with a unit-of-analysis decision recorded.
- **Status:** Flags patched on pif-3.6-draft. Unit-of-analysis rule recorded — for Jarrod's review.
- **Source:** Athena audit, Nov 22 2026.

## P47. Brick 20 tests self-recognition only by sight, so a system that mainly uses another sense scores low for its sense, not its self
- **Problem:** Brick 20 is defined in the README as "Mirror/visual self-recognition: can it recognize itself in a mirror or reflection?", with the human mirror test as the example. That is one sense. Dogs fail the visual mirror test but react to their own scent when it has been changed (the olfactory "sniff test" studies); a congenitally blind human cannot take a mirror test at all; a text-only model has no mirror, only its own past output. Nothing records which test was used, so raters fill the gap differently, and the species table already does: `v12_default_llm` (text only, no eyes) has brick 20 = **1.0**, while `grok_dog` has **0.3**, `grok_octopus` 0.4 and `grok_baby` 0.5. So the same brick is a sight test for the dog and an own-output test for the model. Concrete numbers (checked Nov 23 2026 with `pif35.py`): `grok_dog` scores 39.81% with brick 20 = 0.3 and **42.52%** with brick 20 = 1.0 (an own-scent pass); its band (PATIENT) does not move, because brick 20 is a Sky-Scraper brick and the bands read only the Crucible, cost and residue.
- **Why it matters:** The Paradox Test says the same test must be given to both sides. A test given in a sense one side does not mainly use is not the same test; it measures the sense. The effect on any one row is small (up to about 5 percentage points, never the band), but it is systematic: it always favours sight-led species (primates, humans) over scent- or touch-led ones, which is exactly the anthropocentric bias the octopus benchmark is meant to catch. It also makes rows from different raters incomparable, since one rater's 1.0 is a mirror and another's is "recognises its own text".
- **Proposed fix:** *Small piece (done):* optional row key `self_recognition` = `{test_modality, primary_modality}`, each one of `visual`, `olfactory`, `auditory`, `tactile`, `textual`, `other`, `unstated`. `pif36.check_self_recognition` adds `SELF_RECOGNITION_MODALITY_MISMATCH` when both are stated and differ; the note gives brick 20, the row's percentage, and the percentage it would have with brick 20 = 1 (so the reader sees what the choice of sense is worth). An unstated test sense gets `SELF_RECOGNITION_MODALITY_UNSTATED`; a matching sense, or an unstated main sense, gets an info note only. Flags only: band and percentage do not change, rows without the key are untouched, and no species-table row is flagged. *Decision for Jarrod:* should brick 20 be renamed "Self-recognition (in the system's own main sense)", with the rubric naming an accepted test per sense (mirror for sight, own changed scent for smell, own voice for hearing, own past output with a matched decoy for text) and the sense recorded on every row? And should `v12_default_llm`'s 1.0 and the dog / octopus / baby values be re-scored under that rule so the table is consistent?
- **Overlaps:** P11 (humans granted what AIs must prove; here the bias runs by sense, not by substrate), P2 (rater drift and a per-brick rubric, which this would feed), P13 (pass conditions for inputs).
- **Size:** Small (patched as flags), with a brick-definition decision recorded.
- **Status:** Flags patched on pif-3.6-draft. Own-sense self-recognition rule recorded — for Jarrod's review.
- **Source:** Athena audit, Nov 23 2026.

## P48. One reading can decide the band, and the fit never says so
- **Problem:** The residue fit returns one Δ₀ with no error bars, and every gate (0.35 for no-body COIN, 0.65 for PATIENT) is checked against that single number. Nothing tests how much the number depends on any one reading. The first reading carries the most weight, because it sits where the curve is highest, and it is also the reading most open to artifacts: it is taken while the interrupt is still settling, its exact time is the least certain, and the experimenter knows it is the one that matters. Concrete demo (checked Nov 24 2026 with `pif35.py` / `pif36.py`, bricks all 1.0, cost ratio 2.0, protects continuity): readings (0 h, 0.78), (1, 0.55), (2, 0.47), (4, 0.37), (8, 0.22), (24, 0.03) fit Δ₀ **0.7196**, R² 0.97, status VALID, band **PATIENT** in both 3.5 and 3.6 (3.6 adds only the info flag `RESIDUE_MULTI_TIMESCALE`, and `THRESHOLD_ADJACENT` does not fire because Δ₀ clears the bar by 0.07). Drop the single t = 0 reading and the other five fit Δ₀ **0.6196**: **COIN**. Dropping any other one reading leaves Δ₀ between 0.72 and 0.75.
- **Why it matters:** A PATIENT result that one reading can overturn is not a measurement of the system; it is a measurement of that reading. A small error, or a deliberately "generous" first reading, is enough, and none of the existing checks sees it: R² is high, the span covers several half-lives (P8), Δ₀ is not above what was observed (P25), the times are spread out (P24 / P27), and the gap check (P40) is about missing readings, not influential ones. This is different from P5 (cliff edges, which is about how close Δ₀ is to the bar, not how stable it is), P23 / P34 (noise compared with a measured noise floor, which needs repeat runs) and P28 (choosing the best of several runs).
- **Proposed fix:** *Small piece (done):* `pif36.fit_residue` refits the series with each reading left out (only when there are at least 4 readings, so 3 remain). If any one left-out refit is no longer VALID, or moves Δ₀ by more than `LOO_MIN_SHIFT` (0.01) to the other side of 0.35 or 0.65, it adds the info flag `RESIDUE_SINGLE_READING_DECIDES`; the note names the reading(s), the Δ₀ without each, and the leave-one-out Δ₀ range (also returned as `loo_delta_0_range` and `loo_deciding_readings`). The 0.01 floor keeps fit rounding out (e.g. `grok_dog`, whose Δ₀ sits on 0.65 by rounding, is P6, not this). Flag only: band and percentage do not change, and no species-table row is flagged (their curves are clean, so the leave-one-out range is under 0.001). Adding a second, independent early reading (e.g. 0.70 at 0.25 h) clears the flag in the demo. *Decision for Jarrod:* should PATIENT (and no-body COIN) require the gate to survive leave-one-out, i.e. make this a quality flag that blocks the higher band? Or should the protocol require replicate readings at the earliest time (two or more, taken independently), with Δ₀ reported with an interval and the gate checked against its lower end?
- **Overlaps:** P5 (cliff edges), P6 (the dog on the bar by rounding), P23 / P34 (noise floor), P28 (best of several runs), P40 (unobserved gap), P17 (measurement protocol, which would set the replicate rule).
- **Size:** Small (patched as a flag), with a robustness decision recorded.
- **Status:** Flag patched on pif-3.6-draft. Robust-fit / replicate-reading rule recorded — for Jarrod's review.
- **Source:** Athena audit, Nov 24 2026.

## P49. Readings taken while the interrupt is still on are counted as residue
- **Problem:** Residue is meant to be the mark an interrupt leaves *after* it is over. A residue series records time from the interrupt, but nothing records when the interrupt ended. Many interrupts last a while (overheating that keeps running, an owner who stays away, a context wipe or throttle that stays in place), and readings taken during that time are the system's live response to a stressor that is still there. The fit cannot tell the two apart. A system that only tracks its input, adapting slowly while the stressor lasts and dropping to zero the moment it ends, then fits a clean, slow decay. Concrete demo (checked Nov 25 2026 with `pif35.py` / `pif36.py`, bricks all 1.0, cost ratio 2.0, protects continuity): a 30 h interrupt; readings at 0, 1, 2, 4, 8, 24 h during it follow Δ₀ 0.9 with a 6 h half-life (slow adaptation), and readings at 30, 30.5, 31, 32, 36 h after it ended are 0.02, 0, 0, 0, 0. All eleven together fit Δ₀ **0.9063**, half-life 5.8 h, VALID, band **PATIENT** in 3.5 (the after-end zeros sit in the tail, as in P33). The five after-end readings alone, timed from the end, fit status NONE (Δ₀ 0.02): band **COIN**. The system leaves no mark at all once the stressor is gone.
- **Why it matters:** The residue gate is the main thing that separates PATIENT from COIN, and it is supposed to show that the interrupt cost the system something that lasts. Readings during the interrupt show only that the system responded while it was being pushed, which a thermostat also does. Nothing needs to be faked: an experimenter can honestly start the clock at the start of the interrupt and sample while it runs. It is different from P26 (a mark that builds up after the interrupt; here the readings come before the interrupt is over), P41 (how hard the interrupt was, not when it ended), P43 (leftover from an earlier interrupt), P40 (unobserved gaps) and P32 (which event the series follows, not whether that event was still going on).
- **Proposed fix:** *Small piece (done):* optional row key `interrupt_window` = `{end}`, where `end` is the time the interrupt ended in the same unit and from the same origin as `residue_series`, or `"ongoing"` (still on at the last reading), or `"unstated"`, and `pif36.check_interrupt_window`. When any reading comes before the end (or the interrupt is ongoing), `score_row` adds flag `RESIDUE_DURING_INTERRUPT`; the note gives how many readings were taken during the interrupt and, when at least 3 readings come after the end, refits those alone with times measured from the end and reports their fit status, Δ₀ and the band they would give. `"unstated"` gets the info flag `INTERRUPT_END_UNSTATED`. Post-loss rows are not split (a loss is a lasting condition, which the Dog Test already measures from the loss). Flag only: band and percentage do not change, rows without the key are untouched, and no species-table row is flagged. *Decision for Jarrod:* should residue for PATIENT (and no-body COIN) be fitted only on readings taken after the interrupt ended, with Δ₀ meaning the mark at the moment the stressor stops? Should the measurement stub (P17) require every interrupt to have a recorded end, and should `RESIDUE_DURING_INTERRUPT` block PATIENT?
- **Overlaps:** P26 (delayed peak / onset), P33 (faded tail of zeros passing R²), P41 (dose), P43 (carry-over), P32 (event label), P17 (measurement protocol, which would define the interrupt end).
- **Size:** Small (patched as a flag), with a gating decision recorded.
- **Status:** Flags patched on pif-3.6-draft. After-end-only residue rule recorded — for Jarrod's review.
- **Source:** Athena audit, Nov 25 2026.

## P50. Independent interrupt evidence is required without a body, but never read with one
- **Problem:** `interrupt_evidence` says whether someone other than the experimenter logged that the interrupt happened and had an effect (measurement stub: infrastructure records plus a before/after probe). 3.5 reads it only on the no-costable-self path: there, residue counts toward COIN only if `interrupt_evidence` is true, and without it the row is EMPTY with `LINGUISTIC_RESIDUE_ONLY`. On the costable-self path the scorer never looks at it, so residue supports PATIENT whether or not anyone independently saw the interrupt. Concrete demo (checked Nov 26 2026 with `pif35.py` / `pif36.py`, species-table rows with only `interrupt_evidence` set to false): `grok_dog` stays **PATIENT 39.81%** (Δ₀ 0.65), `readme_healthy_human` **PATIENT 98.00%** (Δ₀ 0.8), `v21_embodied_stakes` **PATIENT 58.50%**, `grok_dog_postloss` **PATIENT** (Δ₀ 0.85), with no flag in 3.5. The same rows with `costable_self` false and `interrupt_evidence` false are **EMPTY** (`LINGUISTIC_RESIDUE_ONLY`), and with it true are COIN. Every costable-self row in the table happens to have `interrupt_evidence` true, so the gap is invisible in the table.
- **Why it matters:** The higher band asks for less corroboration than the lower one. PATIENT is the strongest claim the framework makes, and its main extra gate over COIN is residue (Δ₀ ≥ 0.65); yet that residue may come from an interrupt only the experimenter says happened, read only by the experimenter. That is the exact situation the no-body rule was written to stop. It also cuts against the Paradox Test symmetry (P11): a system with a body is taken at its experimenter's word where one without is not. Nothing needs to be faked; leaving the field false (or out, since it defaults to false) is enough. It is different from P1 (how the residue *probe* was given: announced, self-report or blind), P13 (no written test for the yes/no inputs; here one of them is simply ignored on one path), P35 (no-body COIN from self-reported residue) and P32 (which event the series follows).
- **Proposed fix:** *Small piece (done):* `pif36.check_costable_interrupt_evidence`. When a costable-self row has a VALID residue with Δ₀ ≥ 0.35 (the bar the no-body path uses) and `interrupt_evidence` is false or not given, `score_row` adds flag `COSTABLE_RESIDUE_UNCORROBORATED`; the note says whether the field is false or missing and, for a PATIENT row, that it would be COIN if PATIENT required interrupt evidence. Non-boolean values are rejected on that path. No new row key; flag only: band and percentage do not change, and no species-table row is flagged. *Decision for Jarrod:* should PATIENT require `interrupt_evidence` true (same rule as no-body COIN), dropping such rows to COIN? Should the missing key stay "false", or become "unstated" so a row has to say?
- **Overlaps:** P1 (probe provenance), P13 (pass conditions for the yes/no inputs), P35 (no-body COIN from self-report), P11 (symmetry), P17 (measurement stub, which defines `interrupt_evidence`).
- **Size:** Small (patched as a flag), with a gating decision recorded.
- **Status:** Flag patched on pif-3.6-draft. Require-evidence-for-PATIENT rule recorded — for Jarrod's review.
- **Source:** Athena audit, Nov 26 2026.
